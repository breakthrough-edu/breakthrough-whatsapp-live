# Playbook: Resident Workers (常驻物: 你不在场也在跑、会动手的东西)

> 料源: 三支最会静默失败的常驻物实填六格, 逼出三个真洞; 再把全部自动化逐支盘点一次, 看哪些动作该过审批卡。每个洞都付过真的代价, 下面照原样讲, 但拿掉了是谁的系统。这份随 WhatsApp Live kit 出货, 却不限于 WhatsApp: 以后你建任何 bot、watcher、排程, 都先读这一份。kit 装在 `~/.claude/skills/breakthrough-whatsapp-live/`; 文中「我们默认」的几条, kit 的 `references/defaults-and-why.md` 有同一条与在哪改。

## When to run it

要**新建或改动**一支会自己醒来、会写东西、而你不在场时也在跑的程序, 就先读这一份。形状不限:

- 聊天 bot (Telegram、Slack 或其他平台上会接指令、会动手的那种)
- launchd 常驻程序 / folder watcher (盯一个夹, 进档就处理)
- 排程 job (一次性改公开页的排程、每天早上的简报)
- WhatsApp Live 本身就是三支: daemon · 晚间进料口排程 · daemon 里的档案 run

只读、只推给你自己看的那种也算常驻物, 六格照填, 只是审批卡那一章多半答「不需要」。

⛔ 装好之后才补六格是倒过来的: 六格是**动手前**写在登记簿那一行的, 写不出来的那格当场就是要先解决的洞。

## What to weigh

### 一 · 六格: 写不出来的那一格就是洞

每一支常驻物在你的常驻物登记簿 (一份列出各台机上所有常驻程序的档; 还没有就先开一份) 自己那一行底下答六格。⛔ 不另开档: 改它的停法时, 人只会去改登记簿, 副本一定会漂。

```
读: 只读哪些路径 / 哪几张表
写: 会动哪些东西; 「永不写」也是合法答案
上限: 超时秒数 · 重试次数 · 一次最多发几条
停: 停的那几行命令; 停了会不会留半截; 重开机后还会不会自己回来
证明: 怎么知道它真的成功了, 不是 exit 0
回滚: 盖回哪份备份 · 删哪几笔
```

要掂量的不是格子填满没有, 是**哪一格答不出来**。实填逼出来的洞, 正好是最常见的三种:

- **「停」停了其实没停。** 两支写正式资料库的 worker 只做了 `launchctl bootout`, plist 留在 `~/Library/LaunchAgents/`「方便下次重开」。四天后那台机切换帐号重新登入, launchd 把 LaunchAgents 全部载回, 两支自己复活, 连着正式资料库照真跑了三天, 登记簿上还写着「停」。`bootout` 只管到下一次登入或重开机。⇒ 「停」这一格要答到**重开机之后**。我们默认三件一起做: `launchctl bootout` · plist 搬出 `~/Library/LaunchAgents/`, 放进一个带日期的暂停夹 (例如 `~/Backups/launchd-paused-<日期>/`) · 依赖它的警报 (例如「多久没跑就喊」的开关) 同时暂停, 否则明天起天天误报。登记簿那一行写清楚 plist 放在哪、重开时怎么反过来做 (搬回、bootstrap、重开警报)。不用 `launchctl disable`: 它撑得过重开机, 但「停了」这个状态藏在 launchd 的资料库里, `ls LaunchAgents` 看起来像装着在跑, 状态又跟肉眼看到的不一样, 而这个洞本来就是这样出的事。
- **「证明」只有 exit 0。** 一支把发票建进会计表的 folder watcher, 每次都「成功」。某天一张发票丢进夹里一分钟后被人改了档名: 第一轮照旧路径建好记录, exit 0; 用旧档名搬档失败, 只进了 stderr, 脚本照记成功; 改名又让 launchd 再排一轮, 看到「新」档名就再建一笔。同一张发票入账两次, 七周没人发现, 最后也不是对账发现的, 是填六格时读 log 逼出来的。⇒ 证明要是一个从外面读得回来的东西 (回读到的记录 id、查重结果), 不是程序自己说它跑完了。会写外部资料的自动化, 另外守四条:
  - 写入前先对输入算指纹 (例如 md5) 查本机账本, 处理过的就不交给模型; 改名、重传、复制都挡得住。指纹要在交给模型**之前**算: 跑到一半输入被改, 之后算的就不是原来那份。
  - 搬档失败当一件事处理, 不能只留在 stderr: 那是「输入在跑的时候变了」的唯一迹象。
  - 每一道闸挡下的东西, 都落在人会看的地方 (例如失败夹里的一个 `.txt`); 只写进 log 的警告等于没有。
  - 查到重复就留证据给人判, 自动化不自动删; 删记录要人点头。
- **从机器外面看不出它还活着。** 一支聊天 bot 挂住的时候, 跟「没人叫它」长得一模一样。⇒ 会静默的东西要有一个你不用去查 log 就看得到的存活讯号 (WhatsApp Live 的做法: 每天早上一则日报, 安静日也发一句说它活着)。

⭐ 判准是**静默失败**, 不是重要: 坏了会大声喊的排后面, 坏了没人知道的先填。

### 二 · 审批卡: 哪些动作要你按了才做

从登记簿那一行的六格就读得出要不要卡。**任一条成立就要上卡**:

1. **别人看得到**: 「写」那格出现你以外的收件人或群、公开页 (落地页、官网)。
2. **碰真钱**: 「写」那格出现会计表或管钱的资料库。
3. **收不回来**: 「回滚」那格答「无」(删除、已发出的讯息、推播)。
4. **写进去的值是 AI 生成的**, 不是固定参数。

**不用上卡**: 只读 · 只推给你自己 · 确定性、幂等、可以重算覆写的同步 (像每几个小时刷一次的报表数据) · 人已经在表单里自己填了参数、自己按了提交。能逆的动作不上卡, 改成给「撤销」加一道二次确认。

一个套用的例子: WhatsApp Live 的档案 run 整份重写人物档, 是 AI 生成的字写进 vault, 照第 4 条该上卡。kit 默认不上卡, 改用三道: 验档器 (锁你的手记与口述标记、锁链接、锁备注、stage 封顶) · 放档前留三版备份加 filing-log 一行 · 进料口只进暂存档, 真挂 task 或建日历要你逐条点头。代价是你信得过验档器; 要改成先出候选、按了才放, 代价是夜批每晚最多按 `dossier.nightly_cap` 次。同一题的另一个答案是永不自动发送 WhatsApp: 板上的草稿框就是那张卡, 你按 send 就是按卡。

⚠️ 抄步骤的人最容易错的两个地方:

- **把「按了才写」当成「写的就是卡上那版」。** 一支群秘书 bot 做到了前者, 没做到后者: 草稿按「群 + 类型」存, 按钮没带草稿编号, 同一个群先后出两张卡, 按旧卡会写进新草稿。
- **在全工具的 bot 上靠 prompt 叫它出卡。** 指示写得再清楚, AI 都可以不出卡直接做, 按下之后执行的也是它重新生成的那版。全工具 bot 的闸只能落在工具调用那一层, 而那一层的命令样式本质上是黑名单, 一定会漏, 所以要配一道侦测 (log 里出现写入动作却没经过卡, 就喊)。同一个道理见下面第三节。

**反向检查, 防判准太宽**: 一支上了卡的常驻物, 三十天里每一张卡你都原样按过, 没改过、没拒过, 就代表这支的判准太宽, 该收窄。卡太多跟没有卡一样, 你会开始不看就按。

### 三 · 验闸: 要问执行环境, 不能问被关的那一个

一个没被实测过的闸, 是一个信念, 不是一个闸。真实案例: 一支要求唯读的 bot 设了三层工具闸, 上台前两题验收都过了 (问家规答对, 叫它建档它拒绝, 而且理由讲得很好), 可是 log 里被挡下的工具调用是零: 它根本没伸手, 只是读了 system prompt 就口头拒绝。把 CLI 自己回报的工具清单印出来一看, 载入的是二十几支: 点名封掉的确实不在, 但另外十几支从来没被允许过的自己进来了, 其中能派子代理 (一条绕过唯读的写入路)、能排定期工作、能找同机其他 session 的那三支最要命。`--allowedTools` 不是严格白名单, 它只加不减。同一个洞在前一支 bot 上漏的是同样三支, 解法当时就写下来了, 却写在那支 bot 自己的说明里, 所以建下一支时没人读到。

- ⛔ 别拿「它拒绝了」当闸有效的证据。模型说「我没有那个工具」, 可能只是在复述你给它的 system prompt; 要拿执行环境自己的说法 (CLI 回报的 `system/init` 工具清单)。「档案没被建出来」证明的也只是这一次没事。
- ⭐ 设完之后印一次实际生效的清单, 跟你以为的比对, 差一支都算没设对。黑名单再配一道每次执行都跑的侦测: 多出来的工具就大声喊 (log 加当场告诉你)。黑名单挡已知的, 侦测抓未来的。
- ⛔ 闸自己声明的安装方式要读, 不能推。一支守卫档头写着要挂 `Write` 与 `Bash` 两个 matcher, 只挂一边看起来跟装好了一模一样, 用 shell 重导向写档就从旁边绕过去。看过一个控制在别处生效, 不等于它在你这里装好了。
- ⛔ 验闸要跑它自己声明的探针, 而且照它写的方式跑。同一份 JSON 输入, zsh 的 `echo` 会把字串里的 `\n` 展开成坏掉的 JSON, 守卫读不懂就放行; 换成 `printf` 就回拦住。一个测出来是坏的结果, 先怀疑测法, 再怀疑被测的东西。
- ⭐ 一个只写在某个产物里的教训, 只对那个产物有效。像这样的坑, 写进 playbook 或 Lessons, 让下一次「给某个东西设权限」时不管是第几支、跑在哪个平台, 都先撞到它。

### 四 · 排程与 launchd 底下的两个坑

- **排程第一次启动, 要先判「今天该不该补跑」, 默认不补。** 夜批写成「过了 02:30 而今天没跑过就跑」, 常驻时是对的; 白天为了改码 kickstart 一次, 新进程一起来看到「今天没跑过」, 当场跑了一轮夜批: 拿到的是半截对话, 两个重写里有一份掉了一整节, 而且改码期间每重启一次就再触发一次。⇒ 启动时已经过了排程点而今天没纪录, 就把今天记成跑过, 等下一个点; 要补跑用指令明说, 不靠启动时的巧合。「上次跑的日期」这种状态第一次启动就写好, 空值不能被读成「该跑」。会花钱或会改档的排程, 第一次上线先用假时钟或短窗冒烟一次, 看它在「刚启动」「刚过点」「跨日」三个时刻各做什么。改码后的 kickstart 也是一次启动: 每个排程都要经得起白天被重启十次。
- **launchd 直起的 python 有 Full Disk Access, 它的子进程没有。** 子进程 (ffmpeg、whisperkit、claude、任何 CLI) 一碰受保护的夹, 就卡在 `open()` 等一个没人答的授权弹窗: 零输出、零 CPU、越等越久, 不是报错。第一刀 `sample <pid>` 看堆叠是不是停在 `__open`, 第二刀 `pgrep -P <pid>` 看子进程。修法: launchd 的程式换成有 Full Disk Access 的 node, 由它起真正的脚本。⛔ 在 `ssh` 里跑得通不等于 launchd 底下跑得通, 两条路的授权与 keychain 都不同; 验收一律走 launchd 那条 (指令档或 kickstart)。

## The moves

**建之前**

1. 在登记簿写下六格。答不出的格子先解决, 或明写「答不出: <为什么>」并开一张 task。
2. 用上面四条对「写」与「回滚」两格, 决定哪些动作要过卡。
3. 登记簿那一行同时写明: 停法 (含重开机后)、证明读什么、装在哪一台机。写机器的名字, 不写「这台」: 登记簿会同步到别台机, 指示代词一到另一台就变成假话。

**做审批卡**

4. **一卡一动作, 卡上钉完整的将执行内容**: 目标系统、表与记录 (或收件人名字加 id) · 逐字原文或每个字段的值 · 改动的现值与新值 · 查重结果 (同一张发票号已有几笔) · 一个「未写入」标签。
5. **钉版本**: 按钮值带草稿编号加内容指纹; 执行时按编号只取一次, 指纹对不上或过期就拒绝, ⛔ 绝不去取「这个群最新的那份草稿」。
6. **执行的是程序, 不是 AI**: 按下之后跑写死的命令, 参数只来自卡上钉住的那份。要让 AI 参与, 就拆成两段: AI 只负责读出内容 (吐结构化结果), 程序负责查重、出卡、执行。
7. **两层锁**: 用过的卡改成已处理 (防同一个人按两次); 业务层草稿只取一次 (防两个人同时按); 每一个失败分支都把草稿放回去, 否则那张卡永久失效。
8. **执行完回读**: 拿到记录 id 或回读到新值才算成功, 再把卡改成「已完成」。

**上线之后**

9. 按六格的「证明」真的验一次 (不是看绿勾), 再按「停」真的停一次、**重开机一次**, 确认它没有自己回来。
10. ⛔ 接线细节 (待办档的格式、Telegram 的 inline keyboard、其他平台的卡片回调事件) 不写进这份, 住各支自己的登记簿那一行或项目夹。
